RAG 원리

1. RAG의 기본 구조

RAG는 Retrieval-Augmented Generation의 약자입니다. Retrieval은 관련 정보를 찾는 검색, Augmented는 찾은 정보를 모델의 입력에 보태는 보강, Generation은 그 입력을 바탕으로 답을 작성하는 생성입니다. 예를 들어 질문과 관련된 규정 조항을 먼저 찾고, 그 조항과 질문을 함께 언어모델에 전달해 설명을 작성하게 합니다.

검색 대상은 PDF나 업무 매뉴얼에 한정되지 않습니다. 웹페이지, 데이터베이스의 조회 결과, 검색 가능한 지식 저장소도 대상이 될 수 있습니다. 이 수업에서는 법령·판례·공개 안내문을 다루기 때문에 문서 기반 사례로 설명합니다. 검색한 자료를 사용해도 모델이 잘못 해석하거나 근거 밖 내용을 덧붙일 수 있어 답변 범위와 검사가 함께 필요합니다.

참고: Google Cloud · RAG의 개념

2. 자료 등록과 답변 생성의 두 과정

문서를 올리는 일과 답변을 만드는 일 사이에는 여러 처리가 있습니다. 먼저 문서를 읽을 수 있는 형태로 추출하고 검색용 색인을 준비합니다. 질문이 들어오면 그 색인에서 관련 자료를 찾고, 필요한 부분을 골라 모델에 전달합니다. 문서 수정은 준비 과정에, 질문 표현 변경은 질문 처리 과정에 영향을 줍니다.

구분처리 흐름남겨야 할 연결 정보
자료 준비수집 → 본문 추출 → 청킹 → 메타데이터 → 색인원문, 문서 ID, 버전, 조문·페이지, 접근 범위
질문 처리질문 해석 → 검색 → 근거 선택 → 입력 구성 → 생성검색 질문, 사용한 근거, 생성에 전달한 구절
답변 확인인용 대조 → 조건 확인 → 답변 또는 확인 보류어느 주장을 어떤 원문이 뒷받침하는지

자료가 색인에 없다면 질문 문장을 정교하게 바꾸어도 그 자료를 검색할 수 없습니다. 반대로 자료 준비가 정상이어도 질문의 날짜나 대상 업무가 빠지면 다른 조건의 근거를 찾을 수 있습니다. 어느 과정의 문제인지 확인해야 수정할 위치가 정해집니다.

참고: Google Cloud · RAG 인프라 구성

3. 본문 추출과 OCR

문서 파일에는 글자뿐 아니라 표, 이미지, 머리말, 각주가 들어 있습니다. 스캔 문서는 OCR로 글자를 읽어야 하고, 표에서는 열 제목과 값의 관계가 유지되어야 합니다. 화면상 파일명이 보이더라도 본문이 비었거나 메뉴만 수집됐다면 검색할 근거가 충분하지 않습니다.

예를 들어 원문에 “승인 전에는 내려받을 수 없다”라고 적혀 있는데 추출본에서 “없다”가 빠지면 의미가 뒤집힙니다. 이후 검색과 생성이 정상적으로 실행돼도 잘못 추출된 문장을 근거로 답할 수 있습니다. 따라서 원문의 제목·조건·예외·표본 문장을 추출 결과와 먼저 대조합니다. 아래 예시는 원리 설명을 위해 만든 교육자료 열람 규칙이며 HUG 규정이 아닙니다.

4. 청킹: 문서를 나누는 기준

청크는 검색에 사용할 문서의 일부 구간입니다. 너무 큰 구간에는 관련 없는 내용이 섞이고, 너무 작은 구간에는 문장의 전제나 예외가 빠질 수 있습니다. 조항 번호와 제목, 본문과 단서, 표 머리글과 행을 함께 보존하는 기준이 필요합니다.

교육용 가상 원문 EDU-02
“열람 예약 변경은 열람 시작 전까지 신청 화면에서 요청한다. 열람 시작 이후에는 담당자 확인이 필요하다.”

“시작 전까지 신청 화면에서 요청한다”만 검색되면 시작 이후의 처리 방법을 놓칩니다. 두 문장을 함께 전달하면 시간 조건을 나누어 답할 수 있습니다. 겹치는 구간을 두는 방법도 경계 누락을 줄일 수 있지만, 중복 근거가 늘 수 있으므로 실제 질문으로 확인해야 합니다. 적절한 청크 길이는 문서 구조와 질문에 따라 달라집니다.

참고: Microsoft · 문서 청킹

5. 메타데이터: 문서 정보와 적용 기준

검색용 본문과 함께 문서명, 문서 ID, 원문 주소, 조문·페이지, 버전, 시행일, 열람 권한을 저장합니다. 이러한 부가 정보를 메타데이터라고 합니다. 질문의 기준 날짜에 맞는 문서를 검색하고, 답변에 인용된 내용을 원문에서 확인할 때 사용합니다.

예를 들어 신청 방법이 개정됐다면 질문에서 묻는 시점에 유효한 규정을 찾아야 합니다. 개정 전후 문장이 비슷하더라도 적용되는 날짜가 다를 수 있기 때문입니다. 사용자에게 열람 권한이 없는 문서는 검색 결과와 모델 입력에서 제외하고, 인용 링크를 열 때도 권한을 확인해야 합니다.

6. 임베딩과 의미 검색

임베딩은 텍스트 등을 숫자 배열인 벡터로 표현하는 방식입니다. 질문과 문서를 호환되는 임베딩 모델로 표현하면 단어가 완전히 같지 않아도 의미가 가까운 구간을 찾는 데 사용할 수 있습니다. 예를 들어 “신청 내용을 바꾸고 싶다”라는 질문으로 “예약 변경”에 관한 문장을 찾는 경우입니다.

벡터가 가깝다는 것은 해당 표현 체계에서 비슷하다는 뜻입니다. 같은 업무인지, 최신 규정인지, 질문의 조건을 충족하는지는 별도 확인이 필요합니다. 유사도 점수 0.9를 답변이 90% 정확하다는 뜻으로 읽으면 안 됩니다. 사용하는 모델이나 검색 방식에 따라 점수의 의미도 달라집니다.

참고: Microsoft · 벡터 검색

7. 키워드 검색·벡터 검색·하이브리드 검색

방법찾는 기준확인할 점
키워드 검색단어·문구 등 텍스트 표현의 일치사건번호·조문 번호·상품명과 같은 정확한 표현
벡터 검색질문과 문서 표현의 의미적 유사성표현이 달라도 찾는지, 다른 업무의 유사 문장이 섞이는지
하이브리드 검색텍스트 검색과 벡터 검색의 결과를 결합각 방식의 결과를 어떤 기준으로 합치는지

사건번호가 있는 질문과 “이런 경우 어떻게 하나요?”라는 질문은 필요한 검색 방식이 다를 수 있습니다. 하이브리드 검색은 두 방식의 장점을 함께 쓰는 구성입니다. 결합했다고 항상 개선되는 것은 아니므로 같은 질문과 필수 근거로 비교해야 합니다.

참고: Microsoft · 하이브리드 검색

8. 검색 후보 선택과 재정렬

검색기는 관련 가능성이 있는 후보를 반환합니다. 그 후보를 다시 질문과 대조해 순서를 조정하는 처리를 재정렬, 즉 reranking이라고 합니다. 이후 중복을 줄이고 입력 길이를 고려해 생성 모델에 전달할 구간을 고릅니다. 검색에서 찾았어도 이 선택 과정에서 빠지면 답변 생성에 사용되지 않을 수 있습니다.

가령 후보 10개 중 상위 3개를 전달하는 구성이라면 예외 조항이 네 번째에 있어 빠질 수 있습니다. 이 숫자는 처리 단계를 설명하기 위한 예시입니다. 전달 수를 늘리면 필요한 근거가 포함될 수 있지만 관련 없는 내용과 입력 길이도 늘어납니다. 후보 목록과 실제 전달 구간을 구분해 기록해야 원인을 진단할 수 있습니다.

참고: Microsoft · 검색과 재정렬

9. 복합 질문의 분해

“접수했으니 승인됐고 오늘 자료를 받을 수 있나요?”에는 접수 사실, 승인 여부, 내려받기 조건이라는 서로 다른 확인이 들어 있습니다. 검색 전에 이 항목을 나누면 어떤 문장이 필요한지 구체적으로 정할 수 있습니다. EDU-03의 가상 규칙이 “담당자가 승인한 경우 자료를 내려받을 수 있다”라면 접수 사실만으로 승인 여부를 채울 수 없습니다.

이 수업의 세 노트북도 검색 범위를 나누기 위한 구성입니다. A에서는 규정과 조건, B에서는 문의에 대한 설명 근거, C에서는 제출 목록과 확인 항목을 조회합니다. 각자 세 노트북을 사용해 필요한 근거를 확인합니다.

10. 검색 근거를 이용한 답변 생성

모델의 입력에는 질문, 답변 지침, 선택한 근거가 함께 들어갑니다. “자료로 확인되는 사실”, “조건에 따른 설명”, “자료만으로 확인할 수 없는 사항”을 구분하게 하면 각 문장의 성격을 확인하기 쉽습니다. 입력에 근거가 없는데 답변에만 구체적인 날짜나 금액이 나오면 무엇을 바탕으로 썼는지 대조해야 합니다.

인용은 원문을 확인할 수 있는 연결입니다. 인용번호가 존재하는지, 구절이 실제 원문과 일치하는지, 그 구절이 해당 주장을 지지하는지, 현재 사안의 조건에 맞는지를 나누어 확인합니다. 한 문서에서 세 구절이 나왔다고 문서 세 개를 확인한 것은 아닙니다. 실제 C 응답의 인용 귀속 오류와 수정 과정은 실행 흐름 단원에서 볼 수 있습니다.

11. RAG 오류가 발생하는 단계

관찰먼저 확인할 위치수정 방향
필요한 문장이 추출본에 없음자료 수집·OCR·본문 추출원문과 추출 결과를 대조
추출본에는 있지만 검색 후보에 없음색인·질문·필터·검색 방식필수 근거가 후보에 들어오는지 시험
후보에는 있지만 전달 근거에 없음재정렬·중복 제거·입력 길이빠진 조건을 포함하도록 선택 기준 점검
올바른 근거를 전달했지만 결론이 다름생성 지침·질문 조건·해석오류 문장과 원문을 연결해 수정
설명은 맞지만 개별 사실이 미제공실제 입력의 정보 부족사실을 추정하지 않고 추가 확인

검색 실패에 출력 형식만 바꾸거나, 사실 부족에 재검색만 반복하면 문제가 남을 수 있습니다. “답이 틀렸다”라는 한 가지 표시 대신 어느 단계에서 무엇이 빠졌는지 남기는 이유입니다. 검색 품질은 필요한 근거를 찾았는지, 답변 품질은 그 근거로 올바르게 설명했는지를 각각 봅니다.

12. NotebookLM 실습과 자체 RAG 구축

NotebookLM에서는 자료를 등록하고 선택한 뒤 질문과 인용 원문을 확인합니다. 이 과정을 통해 자료 범위, 질문 표현, 인용과 답변의 관계를 살펴볼 수 있습니다. 화면에서 확인하지 못한 내부 청크 길이·검색 알고리즘·후보 순위를 직접 측정했다고 설명하지 않습니다.

기관용 RAG를 직접 구축하려면 본문 추출, 검색 저장소, 임베딩을 사용하는 경우의 임베딩 모델, 생성 모델, 사용자 인증, 자료 갱신, 원문 연결, 평가가 필요합니다. 파일 첨부도 제품에 따라 전체 문맥 제공이나 검색 처리를 포함할 수 있으므로 첨부했다는 사실만으로 내부 방식을 단정하지 않습니다. 파인튜닝은 모델의 가중치를 조정하는 학습이며, 검색 시점에 근거를 가져오는 RAG와 구분됩니다.

하네스 엔지니어링

13. 하네스 엔지니어링의 구성

모델이 다음 행동을 제안하더라도 실제 파일을 읽거나 도구를 호출하는 일은 실행 환경이 수행합니다. 하네스는 모델에 제공할 정보, 사용할 도구, 실행 순서, 결과 검사, 상태 저장과 종료를 연결하는 구조로 이해할 수 있습니다. 하네스 엔지니어링은 이 구조가 원하는 작업을 안정적으로 이어 가도록 설계하고 수정하는 일입니다.

이 수업에서는 하나의 Claude Code 세션이 세 노트북을 조회하고, 반환된 근거를 모아 초안을 작성합니다. 여기에 실제 도구 반환을 보존하는 실행기, 인용 유무 확인, 결과 파일과 재개 기록을 연결했습니다. 이는 문서 업무를 설명하기 위해 구성한 적용 예시이며, 특정 기업이 정한 HUG 전용 표준 절차가 아닙니다.

14. 프롬프트·컨텍스트·RAG·하네스의 관계

대상주로 정하는 것교육자료 열람 문의의 예
프롬프트해야 할 일과 답변 조건접수와 승인을 구분하고 근거 없는 날짜를 만들지 않기
컨텍스트현재 판단에 제공할 정보원래 문의, 선택 근거, 이전 실행 결과, 현재 상태
RAG필요한 외부 근거의 검색과 전달승인 후 내려받기 조건을 찾아 입력에 포함
하네스도구 실행·검사·상태·복구·종료조회 실패를 감지하고 결과 파일과 완료 기준 대조

컨텍스트 엔지니어링은 현재 모델이 사용할 정보를 선별하고 유지하는 관점입니다. 관련 없는 로그를 계속 덧붙이는 대신 원래 요구, 필요한 근거와 현재 상태를 찾기 쉽게 구성합니다. 하네스는 그 정보 관리에 도구 실행과 결과에 따른 처리를 연결합니다.

참고: Anthropic · 컨텍스트 엔지니어링

15. 워크플로와 에이전트의 차이

워크플로는 정해진 경로에 따라 처리를 이어 가는 구조이고, 에이전트는 모델이 상황에 따라 다음 행동이나 도구를 선택하는 구조로 구분할 수 있습니다. 실제 시스템에서는 두 방식이 함께 쓰일 수 있습니다. 모든 단계를 자유롭게 맡기기보다 어떤 선택을 허용할지 정하는 것이 중요합니다.

이 수업에서는 “입력 확인 → 조회 → 검사 → 초안 → 결과 확인”을 기본 순서로 둡니다. 질문 분해와 근거 설명은 AI가 수행할 수 있지만, 연결되지 않은 승인·지급·발송을 완료했다고 쓰지 않게 합니다. 자율적인 도구 선택이 필요 없는 단계는 명시적인 순서와 검사로 처리할 수 있습니다.

참고: Anthropic · 워크플로와 에이전트

16. 도구 호출의 입력과 반환값

도구를 연결할 때는 도구 이름뿐 아니라 무엇을 입력받고 어떤 상태로 반환하는지 정해야 합니다. NotebookLM 조회라면 노트북 ID, 소스 범위, 질문, 시간제한과 실제 응답이 한 쌍입니다. MCP는 이런 도구 연결에 사용하는 방식이며, MCP가 연결됐다는 사실만으로 답변의 근거가 검증되는 것은 아닙니다.

도구 실행은 여러 단계에서 실패할 수 있습니다. 연결 자체가 끊길 수도 있고, 통신은 끝났지만 반환 본문이 error일 수도 있습니다. 본문이 success여도 인용 구절이 없을 수 있습니다. 각 상태를 확인한 뒤 다음 처리를 결정해야 합니다. 조회 도구의 성공은 최종 검토 결과의 성공과 구분합니다.

17. 실행 결과에 따른 진행·재시도·중단

아래는 실행 원리를 보여 주는 의사코드이며 복사해 실행하는 프로그램이 아닙니다. 핵심은 도구 결과를 받았을 때 무조건 초안 작성으로 넘어가지 않는다는 점입니다.

입력과 현재 상태 읽기
필요한 질문과 사용할 자료 정하기
도구 호출 → 실제 반환 보존

연결 실패 또는 시간 초과:
    허용된 재시도 횟수 확인
    같은 작업의 재시도가 적절하면 다시 조회
    계속 실패하면 실패 단계와 다음 행동을 저장하고 중단
응답은 있지만 근거 부족:
    자료 범위·질문·추가 자료 필요 여부 확인

지침에 “검사하라”라고 적는 것과 프로그램이 실제 반환을 검사하는 것은 구분해야 합니다. 파일 존재나 references 개수는 프로그램으로 확인할 수 있지만, 조문이 해당 결론을 지지하는지는 내용 대조가 필요합니다. 중요한 단계의 진행 조건은 실행기가 확인할 수 있는 형태로 구현해야 합니다.

18. 오류 유형별 복구 방법

실패 종류관찰 예다음 행동

검색 근거 부족답변은 있지만 필요한 조문이 없음질문·자료 범위·원문 수집 상태 확인
내용 해석 오류구절에 없는 승인까지 확정오류 문장과 원문을 대조해 지침 수정

읽기 전용 질의도 반복 실행 비용과 시간이 들기 때문에 재시도 한도를 정합니다. 등록·발송 같은 쓰기 도구는 요청이 실제로 처리됐는데 응답만 끊긴 상황도 고려해야 합니다. 같은 요청을 다시 보내기 전에 처리 여부와 중복 방지 방식을 확인해야 합니다. 이번 실습의 조회와 초안 작성은 실제 고객 발송이나 승인 도구 실행으로 확대하지 않습니다.

19. 상태 저장과 작업 재개

긴 작업이나 새 대화에서는 이전에 무엇을 읽고 만들었는지 누락될 수 있습니다. 작업 ID, 입력·지침 버전, 완료한 단계, 실패한 단계, 결과 파일, 다음 행동을 남기면 다시 시작할 때 확인할 기준이 생깁니다. 상태 메모에 완료라고 적혔더라도 실제 파일과 검사 결과가 일치하는지 다시 확인합니다.

Anthropic의 장기 실행 사례는 개발 작업을 여러 세션에 걸쳐 이어가기 위해 환경 준비와 진행 기록을 남기는 접근을 설명합니다. 여기서는 그 관점을 문서 업무의 결과 파일과 재개 기록에 적용했습니다. 실제 시스템에 필요한 상태와 저장 방식은 업무에 맞춰 정해야 합니다.

20. 파일 검사·내용 검토·최종 처리의 완료 기준

“초안을 저장했다”는 것은 파일 작성 단계의 완료입니다. 사실관계 확인과 업무 검토까지 끝났다는 뜻은 아닙니다. 요청한 파일이 존재하고, 필요한 항목이 있으며, 주요 주장에 근거가 연결되고, 미확인 사실이 남아 있는지를 각각 확인해야 합니다.

검사확인 가능한 증거남는 한계
파일·형식 검사파일 존재, 필수 항목, 도구 반환 상태문장의 타당성을 모두 증명하지 못함
모델 자기점검모델이 적은 오류 후보와 수정 이유사람 검토로 기록할 수 없음
사람 원문 대조직접 확인한 구절과 판단 기록확인하지 않은 범위는 보류
업무상 최종 처리해당 권한과 절차에 따른 실제 처리 기록교육용 초안으로 대체하지 않음

21. Langfuse 실행 추적

Trace는 하나의 요청이 처리되는 흐름이고, 그 안의 관측 항목은 조회·생성·검사 같은 구간을 나타낼 수 있습니다. 입력, 반환, 소요시간, 오류와 재시도 위치를 보면 어느 단계에서 문제가 발생했는지 찾기 쉬워집니다. 필요한 이벤트를 실행기에 연결해야 하며, 프롬프트에 로그를 남기라고 쓴 것만으로 화면이 생기지는 않습니다.

이 수업의 실제 연결에서는 Claude Code가 내보낸 도구 이벤트와 파일 작성 기록을 수집합니다. NotebookLM 내부의 검색 후보 전체나 모델의 숨은 사고를 관찰한 것은 아닙니다. 어떤 정보가 기록되는지, 키·인증정보·업무상 비공개 내용이 포함되지 않는지도 함께 확인해야 합니다.

참고: Langfuse · 실행 추적

22. 지침 개정과 동일 입력 재시험

오류를 발견하면 실제 문제 문장과 그에 대응하는 원문을 먼저 남깁니다. 다음으로 바꿀 지침 절을 정하고, 기본 질문과 자료를 유지한 채 다시 실행합니다. 질문·자료·모델·대화 상태도 함께 바뀌었다면 개선 원인을 한 가지로 단정하기 어렵습니다.

실제 C 사례에서는 같은 기본 질문과 같은 규칙 소스를 두고 지침을 v2·v3·v4로 바꿨습니다. 인용 개수가 늘었을 때도 내용 문제가 남았고, v4에서는 원문 문언·조건부 설명·미확인 항목을 분리한 응답을 관찰했습니다. 버전별 한 번의 실행이므로 반복 안정성까지 증명한 것은 아닙니다. 실제 수정 전후 문장과 남은 문제를 함께 읽으면 검사와 재시험의 차이를 볼 수 있습니다.

23. 내부망 환경의 구성요소

외부망의 NotebookLM 실습을 내부 업무로 옮길 때는 파일만 복사하는 것으로 연결이 완성되지 않습니다. 원문 저장소, 검색과 색인, 필요한 모델, 도구 실행, 인증, 상태와 로그가 각각 어디서 동작할지 정해야 합니다. 같은 웹 화면을 내부에 열더라도 외부 API를 호출한다면 그 통신 경로는 별도 확인 대상입니다.

이번 수업에서 가져갈 수 있는 것은 자료 대장, 검색 질문을 나누는 기준, 근거와 주장의 연결, 도구 반환 검사, 오류별 복구 방법, 재개 기록과 완료 기준입니다. NotebookLM은 검색과 인용을 체험하는 도구이고 Claude Code는 조회와 재가공을 실행하는 환경입니다. 실제 내부망 연결과 업무상 처리는 기관의 승인된 구성에서 별도로 확인합니다.
