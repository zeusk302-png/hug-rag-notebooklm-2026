01 · RAG는 어떻게 답을 만들까요?

청킹·임베딩·검색·생성을 하나의 흐름으로 연결합니다. 도구를 쓰기 전에 원리를 이해합니다.

먼저 완성된 흐름을 상상해 봅니다.

직원이 “신청만 하면 이사해도 되나요?”라고 묻습니다. 시스템은 관련 조문과 적용 조건을 찾고, 그 근거를 질문과 함께 언어모델에 보냅니다. 모델은 근거에 연결된 설명과 확인할 사실을 작성합니다. 잘못된 조문이 검색되면 문장이 자연스러워도 답은 틀릴 수 있습니다.

RAG = 검색으로 보강한 생성

Retrieval은 질문과 관련된 외부 정보를 찾는 과정, Augmented는 찾은 정보를 입력 맥락에 더하는 과정, Generation은 그 맥락으로 답을 작성하는 과정입니다. 여기서 외부란 모델의 학습된 지식 바깥이라는 뜻이며, 인터넷 접속을 뜻하지 않습니다. 내부망 문서 저장소도 검색 대상이 됩니다.

문서는 흔한 검색 대상입니다. 그러나 웹·DB·구조화된 기록도 사용할 수 있습니다. “자료 안에서만 답하라”는 정책을 추가할 수 있지만, RAG라는 구조 자체가 그 정책의 준수를 보장하지는 않습니다.

공식 참고 · Lewis 외 · RAG 원 논문

문서를 준비하는 경로와 질문에 답하는 경로

준비할 때 · 문서를 검색 가능한 상태로 만들기

  1. 수집·추출파일 / OCR / 표
  2. 청킹·메타데이터조문 / 시행일 / 권한
  3. 색인키워드 / 벡터

질문할 때 · 근거를 찾아 답변에 연결하기

  1. 질문·권한 확인사용자 / 업무 조건
  2. 검색·재정렬관련 조각 / 적용 범위
  3. 근거 전달·생성질문 + 근거 + 지시
  4. 인용·검증원문 위치 / 확인 필요

준비 경로는 문서 등록·개정 때 실행합니다. 질문 경로는 사용자가 물을 때 실행합니다. 문서가 바뀌면 색인을 갱신해야 하며, 질문 때에는 읽을 권한이 있는 최신 근거가 들어갔는지 확인합니다.

공식 참고 · Microsoft · RAG 구조

청킹: 문서를 어떤 단위로 검색할까요?

청크(chunk)는 검색할 문서 조각입니다. 너무 작게 자르면 조건과 결론이 떨어지고, 너무 크게 자르면 불필요한 내용이 함께 들어갑니다. 법령은 조·항과 단서, 판례는 사실관계와 판단 근거, 표는 제목·열 이름·행의 연결을 보존하는 설계를 시험합니다.

같은 자료를 자르는 두 방식예상 문제 / 개선
“등기를 마친 경우”와 권리 유지 설명을 다른 조각에 저장검색된 결론에서 적용 조건이 빠질 수 있음
제3조의3 제5항을 조건과 함께 저장하고 조문 식별정보 부착조건과 결론을 함께 대조할 수 있음
블로그·규칙·판례를 한 덩어리에 합침출처의 권위와 적용 범위를 구분하기 어려움

함께 해보기 · 5분: 법령 읽기 파일에서 조건과 결론에 각각 밑줄을 긋습니다. 두 문장을 분리해도 답을 판단할 수 있는지 설명하세요. 정해진 글자 수를 맞추는 것보다 의미 보존 여부를 먼저 확인합니다.

공식 참고 · Microsoft · 청킹 전략

임베딩: 문장을 숫자 좌표로 표현합니다.

임베딩 모델은 문장을 숫자 목록인 벡터로 변환합니다. “집을 옮겨도 되나요?”와 “이사 가능 조건”처럼 표현이 다른 문장의 관계를 검색에 활용합니다. 코사인 유사도는 벡터 사이의 방향이 얼마나 비슷한지 계산하는 한 방법입니다.

유사도는 법률적 적용 가능성이나 정답 확률이 아닙니다. 비슷한 문장인 두 판례도 등기의 법적 근거가 다를 수 있습니다. 질문과 문서에는 호환되는 같은 임베딩 모델을 사용하고, 모델을 바꾸면 기존 벡터의 재생성·색인 변경을 검토합니다.

검색 방식과 재정렬

방식잘 찾는 것확인할 한계
키워드 검색 · BM25 등사건번호·조문번호·업무 코드 같은 정확한 표현다른 말로 표현한 질문을 놓칠 수 있음
벡터 검색표현이 달라도 의미가 가까운 조각유사하지만 조건이 다른 자료가 섞일 수 있음
하이브리드 검색키워드와 벡터 후보를 결합각 검색 점수를 무조건 단순 합산하지 않음. 순위 결합 등을 검토
재정렬 · reranking후보를 질문과 더 정밀하게 비교해 순서 조정추가 계산·지연이 발생. 없는 근거를 만들지는 못함

RAG에 벡터 DB가 반드시 필요한 것은 아닙니다. 키워드 검색으로 찾은 근거를 생성에 연결할 수도 있습니다. Top-k는 가져올 후보 수이며 많을수록 좋은 것은 아닙니다. 중복·무관한 근거와 입력 길이를 함께 평가합니다. 검색 점수의 의미와 임계값은 도구·모델별로 달라집니다.

스스로 확인하기

먼저 답을 생각한 뒤 해설을 펼치세요.

1. 내부망 RAG도 가능한가요?

가능한 구조입니다. 검색 저장소와 모델이 승인된 내부 환경에서 동작해야 하며 실제 장비·도구·정책은 별도로 확인합니다.

2. 유사도 0.9면 90% 정답인가요?

아니요. 벡터의 유사도 점수와 답의 정확도는 다릅니다.

3. 근거가 검색되지 않았는데 프롬프트만 고치면 해결되나요?

검색 대상·추출·청킹·필터·검색 결과를 먼저 점검합니다. 질문 문장을 다듬는 것만으로 없는 근거를 만들 수 없습니다.

근거 검색에서 업무 흐름으로

RAG는 필요한 근거를 찾아 생성에 연결하는 방식입니다. 업무 워크플로는 분류·확인·검색·초안·검토의 순서를 정합니다. Agent는 목표에 따라 행동과 도구 사용을 동적으로 결정하는 구조로 볼 수 있습니다. 이 수업은 Claude Code의 실제 조회와 지침·검사·재시도를 시험하고, 내부망 도구 연결은 설계 과제로 남깁니다.

지침 설계 실습으로 이동

하네스 엔지니어링 · 답변 이후의 실행까지 설계하기

이 수업에서 하네스는 AI가 자료와 도구를 사용해 일을 진행하도록 둘러싼 실행 장치입니다. 지침, 사용할 자료, 도구 권한, 단계 상태, 검사, 오류 복구, 종료 조건을 함께 설계합니다. 긴 프롬프트만 작성하고 끝내면 실패한 도구 호출을 알아채지 못하거나, 다음 실행에서 같은 일을 반복할 수 있습니다.

이 사례의 실행 순환

사례 읽기 → 미제공 사실 분리 → A/B/C 질문 분해 → 도구 조회 → 상태·인용 검사 → 근거표와 초안 → 미확인 항목 기록 → 종료 또는 실패한 단계 재시도입니다. A/B/C는 업무별 지식 범위이며 서로 다른 세 AI 직원이 자동 협업한다는 뜻은 아닙니다. Claude Code 한 세션이 세 조회 도구를 사용합니다.

도구가 반환됐다는 사실만으로 정상이라고 판단하면 안 됩니다. 통신 반환이 정상이어도 본문의 status가 error일 수 있고, 답변이 생성돼도 references가 비어 있을 수 있습니다. 그래서 실행기에서 반환값을 검사하고, 실패한 단계만 재시도하게 합니다. 같은 시간 초과를 무한 반복하지 않도록 횟수도 제한합니다.

“이어서 해 줘”에만 의존하지 않고 입력 버전, 지침 버전, 이미 조회한 질문과 자료, 실패 단계, 결과 파일, 사람 확인 항목, 다음 행동을 파일로 남깁니다. 재시작 시 이 기록과 실제 파일을 읽어 어디까지 끝났는지 확인합니다. 진행 메모의 완료 표시와 실제 파일·검사 기록이 다르면 완료를 보류합니다.

공식 자료를 수업으로 옮긴 방식

  • Anthropic · Building effective agents (2024.12.19): 미리 정한 워크플로와 모델이 다음 도구를 결정하는 에이전트를 구분합니다. 이 수업은 기본 순서와 검사를 정하고, 질문 분해와 재가공을 AI에 맡깁니다.
  • Anthropic · Effective harnesses for long-running agents (2025.11.26): 세션을 넘어 진행하려면 환경 준비와 다음 세션이 읽을 산출물이 필요하다는 관점을, 우리의 재개 기록과 완료 기준에 적용했습니다. 개발 예제를 HUG 문서 업무 실습으로 바꾼 강사의 적용안입니다.
  • Google ADK · Observability: 에이전트 실행을 관찰하는 도구·연결의 참고 자료입니다. 이 수업에서 Google ADK를 설치하거나 실행한 것은 아닙니다.
  • Langfuse · Claude Code tracing: 공식 연결 방법과 추적 범위를 참고했습니다. 실제 시연은 공개 교육 실행 한 건의 도구 이벤트만 보내는 별도 실행기를 사용했습니다. 전역 대화 수집 플러그인은 설치하지 않았습니다.
