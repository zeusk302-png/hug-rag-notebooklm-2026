06 · RAG를 제대로 구축하려면

문서 처리·검색·모델·권한·갱신을 연결합니다. 내부망 구현 담당자에게 전달할 설계를 작성합니다.

완성 예시: 내부 직원용 규정 질의응답

교육용 설계 예시입니다. 직원은 질문과 기준 날짜를 입력하고, 서버는 직원 권한과 문서 버전을 확인해 근거를 검색합니다. 답에는 원문 위치와 확인 필요 항목이 붙습니다. 아래 구성은 HUG의 확인된 시스템 구성이 아닙니다.

준비할 때 · 문서를 검색 가능한 상태로 만들기

  1. 수집·추출파일 / OCR / 표
  2. 청킹·메타데이터조문 / 시행일 / 권한
  3. 색인키워드 / 벡터

질문할 때 · 근거를 찾아 답변에 연결하기

  1. 질문·권한 확인사용자 / 업무 조건
  2. 검색·재정렬관련 조각 / 적용 범위
  3. 근거 전달·생성질문 + 근거 + 지시
  4. 인용·검증원문 위치 / 확인 필요

1. 업무 범위와 시험 질문부터 정합니다.

처음에는 한 부서의 승인된 문서군과 한 가지 업무로 범위를 제한합니다. 대표 질문, 반드시 필요한 근거, 기대 답, 답하지 말아야 할 범위를 담당자가 함께 작성합니다. “모든 규정을 아는 챗봇”보다 실패 원인을 찾을 수 있는 작은 검색 범위부터 시작합니다.

단계별 설계 워크북 ↓

2. 문서를 추출하고 원문과 대조합니다.

처리확인할 것
PDF·문서·표에서 텍스트 추출제목·조문·단서·표 머리글 보존
스캔본 OCR날짜·금액·부정 표현·작은 글자의 인식 오류
머리말·중복·목차 정리정리 과정에서 업무 조건을 삭제하지 않았는지
담당자 표본 대조원문 페이지와 추출 결과의 대응

준비 완료 기준: 실제 본문과 원문 위치를 찾을 수 있어야 합니다. 파일이 등록됐다는 메시지만으로 통과하지 않습니다. 추출이 깨지면 검색 설정을 바꾸기 전에 입력 자료부터 수정합니다.

3. 청크와 메타데이터를 만듭니다.

청크 레코드 설계 예시 · 내부 데이터 없음

chunk_id: LAW-3-3-5
document_id: LAW
title: 주택임대차보호법
section: 제3조의3 제5항
source_url / page_or_section: 원문 주소와 위치
version / effective_from / effective_to: 버전·유효기간
allowed_groups: 접근 가능한 사용자 그룹
text: 조건과 결론을 함께 보존한 원문 구간
embedding_model / content_hash: 모델 버전과 변경 식별값

상위 문서의 제목·권한·시행일을 각 청크가 참조하게 합니다. 효력 종료일을 모르는데 임의로 만들지 않습니다. 표·단서가 잘리면 구조를 보존한 다른 청킹 방식으로 시험합니다.

4. 검색만 먼저 시험합니다.

생성 모델을 연결하기 전에 질문별로 어떤 청크가 반환되는지 봅니다. 사건번호 질문은 정확히 찾는지, 일상적인 표현은 관련 조문을 찾는지, 비교 질문은 필요한 두 근거를 모두 찾는지 확인합니다. 키워드 검색 기준선을 만든 뒤 벡터·하이브리드·재정렬을 하나씩 비교할 수 있습니다.

시험용 설정 예시: 후보 20개를 검색해 재정렬 후 4개를 전달합니다. 이 숫자는 권장 기본값이나 성능 측정값이 아닙니다. 자료·질문·입력 길이에 맞춰 평가표로 바꿔 봅니다.

5. 권한·버전·근거를 묶어 생성에 연결합니다.

구현 순서 의사코드 · 실행 가능한 프로그램 아님

user = 서버에서 인증한 사용자
scope = 서버가 결정한 문서 접근 범위와 기준 날짜
hits = 검색(질문, scope, 후보 수)
hits = 권한·유효 버전 재확인(hits)
evidence = 재정렬·중복 제거·입력 길이 제한(hits)
if 충분한 근거 없음:
    확인 필요 또는 담당자 이관
else:
    answer = 승인된 모델(질문, 근거, 답변 규칙)
    출처 ID·인용 구간·원문 링크 검사
    답변과 확인 필요 항목 반환

접근 범위는 사용자가 입력한 부서명만 믿고 정하지 않습니다. 권한 없는 본문이 모델에 들어간 뒤 “보여주지 마라”라고 요청하는 방식도 충분하지 않습니다. 인용 원문 열기와 캐시에도 같은 권한 정책을 적용합니다.

6. 내부망 구성 방식을 선택합니다.

구성장점선행 확인
승인된 사내 AI·검색 서비스 연결기존 인증·운영 체계를 활용검색 설정·인용·권한·로그·갱신을 제어할 수 있는지
내부 서버에 검색과 모델 배포자료와 추론 경로를 내부에 구성모델 라이선스·장비·동시 사용자·한국어 품질·운영 인력
기관이 승인한 외부/전용 서비스 연계관리형 기능을 활용할 수 있음망 연계·반출 범위·데이터 보관·인증 등 승인 여부

검색 저장소, 임베딩 모델, 생성 모델, 파일 저장소, 인증, 로그를 각각 어디서 실행할지 정합니다. 내부망 웹페이지를 만들었다고 외부 API 호출도 내부 처리가 되는 것은 아닙니다. 설치 파일·모델 반입, 업데이트 경로와 운영 담당도 정해야 합니다.

RAG를 명시적으로 지원하는 관리형 기능도 있습니다. 예를 들어 Gemini API File Search는 공식 RAG 기능입니다. 이는 “지원하는 도구가 없다”는 뜻을 바로잡는 예시이며 HUG 내부망 사용 적합성이나 도입 승인을 뜻하지 않습니다.

공식 참고 · Google · Gemini API File Search

7. 개정·삭제·운영을 설계합니다.

문서 개정 시 변경된 조각을 다시 추출·색인하고 이전 버전의 유효 범위를 정리합니다. 삭제·권한 변경은 검색 색인·원문·캐시에도 반영합니다. 색인 준비가 끝나기 전 잘못된 버전이 섞이지 않도록 교체 절차를 둡니다.

질문별 검색 청크 ID·문서 버전·모델 버전·소요시간·실패 원인을 기록할 수 있어야 합니다. 로그에 고객 원문을 무조건 보관하지 않고 보관 범위·접근권한·기간을 정합니다. 품질과 함께 응답 지연, 동시 사용, 운영 비용을 확인합니다.

비전공자가 남길 수 있는 구축 산출물

  1. 자료 목록과 최신 버전·관리 담당자
  2. 검색 질문과 필수 근거를 연결한 평가표
  3. 권한·답변 보류·담당자 이관 규칙
  4. 구축 담당자에게 전달할 구성도와 미확정 사항

실습의 마지막에는 워크북의 업무 한 개를 채웁니다. 전산 담당자가 구현할 수 있는 요구사항으로 만드는 것이 목표입니다.

먼저 답을 생각한 뒤 해설을 펼치세요.

1. 파일 등록 후 검색이 안 되면 무엇부터 확인할까요?

원문과 추출된 본문을 비교한 뒤 청크·색인·필터를 확인합니다. 파일 등록 메시지는 본문 수집 성공의 증거가 아닙니다.

2. 권한 없는 근거를 모델에 넣고 숨기라고 하면 충분할까요?

아니요. 인증된 사용자 권한으로 검색 범위를 제한하고 생성에 전달하기 전 다시 확인합니다.

3. 개정 문서를 올리면 기존 색인을 그대로 써도 될까요?

변경된 본문·버전·권한을 색인과 캐시에 반영하고 대표 질문을 다시 시험합니다.
